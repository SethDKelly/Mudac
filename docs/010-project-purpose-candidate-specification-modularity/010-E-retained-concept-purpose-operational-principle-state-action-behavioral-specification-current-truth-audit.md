# Purpose

Determine whether the candidate set produced by 010-D is behaviorally specified deeply enough that 010-F can challenge **specificity, purpose singularity and Concept boundaries from actual behavior rather than names or historical catalog momentum**.

010-E asks:

> For every incumbent or challenger that remains materially relevant after rediscovery, can MUDAC state a representation-independent purpose, operational principle, abstract state, meaningful actions/queries, conceptual guards/effects, invariants, and intrinsic temporal/authority semantics clearly enough to expose what the candidate actually does and what boundary questions remain?

This subgroup does **not** decide the final Concept catalog. It supplies the behavioral evidence that makes the next modularity analysis legitimate.

# Governing specification contract

The adopted Base Phase 003 contract requires a candidate specification to make the following discoverable when relevant:

- defensible purpose;
- archetypal operational principle;
- abstract type/value parameters where useful;
- abstract state — the memory required by future behavior;
- meaningful actions and queries;
- conceptual preconditions/guards;
- effects/postconditions;
- invariants/state constraints;
- intrinsic lifecycle, time, historical, correction and authority semantics;
- deliberate under-specification;
- unresolved modularity/boundary questions.

The specification must remain independent from storage, APIs, UI controls, services, queues, identity providers, framework types or architecture packages.

A candidate does **not** need to pass specificity, independence or genericity yet. It needs enough explicit behavior that 010-F/010-G can test those properties rather than infer them.

# Evidence and authority posture

Current canonical Concept owners remain current incumbent meaning. Phase 002 remains detailed behavioral provenance where that meaning is still compatible. Phase 007-B repaired concise Purpose/State/Actions/Operational-Principle discoverability but its catalog-acceptance conclusion is not protected.

010-E therefore applies three rules:

1. **reuse current semantics rather than restating whole historical specifications** when the canonical owner plus linked current rules are behaviorally adequate;
2. **record missing behavioral precision in this phase** when it is needed to compare candidates but final Concept identity is still unsettled;
3. **do not create canonical challenger Concept pages yet**, because 010-F/010-G may split, merge, reject or reframe them before 010-H convergence.

# Cross-cutting specification observations

## 1. Direct cross-Concept references are not proof of intrinsic dependence

Several incumbent current owners use domain-specific references directly in their prose/state, for example Panel → Judge Participation, Encounter → Panel/Team, Scorecard → Judge/Encounter/Rubric Version, and Publication → Export.

For 010-E this is acceptable as current application meaning because the behavior is still understandable. It is **not** accepted as proof that those referenced types belong intrinsically inside the eventual Concept specification.

010-G must explicitly test whether the same behavior can and should be expressed with generic abstract subject/evaluator/basis/representation parameters. This is a boundary-genericity pressure, not a blocker to 010-E.

## 2. Intrinsic behavior is distinguished from synchronization consequence

010-E treats the following as examples of intrinsic behavior:

- Scorecard owns Draft/Finalized/Amendment semantics;
- Versioning owns successor lineage;
- Alias owns replacement/history of an alternate identity;
- Publication owns deliberate distribution state.

The following remain composition/synchronization questions rather than being imported as intrinsic behavior:

- Competition completion causing Access expiration;
- Encounter participation giving rise to a Scorecard opportunity/obligation;
- Scorecard correction refreshing Aggregate/Rank;
- Competition Finalization establishing an official-outcome declaration;
- Export currency changes affecting Publication decisions.

Phase 011 will later revalidate those synchronizations after boundaries converge.

## 3. Historical truth is intrinsic only where future behavior depends on it

Historical state is retained inside a candidate when its future semantics require it, for example:

- Alias replacement;
- Encounter invalidation/replacement;
- Version lineage;
- Provenance;
- Award revocation/correction;
- Export currency/succession;
- Publication withdrawal/supersession;
- Official Outcome succession challenger below.

Low-level telemetry remains outside these specifications.

## 4. Authority is semantic, not authentication

Candidate specifications state only intrinsic authority conditions such as evaluator authorship, Organizer finalization/exception authority, deliberate publication authority or successor confirmation.

Authentication providers, sessions, tokens, RBAC/ABAC engines and AWS IAM remain prohibited implementation concerns during this phase.

# Challenger C1 — Evaluation Assignment / Obligation

## Purpose

Represent a specific expectation that an evaluator is responsible for producing an independent evaluation of a subject under a declared basis, so the application can distinguish **outstanding, satisfied, excused and reassigned work** without fabricating evaluation evidence.

Purpose pressure: P-01, P-02, P-04, P-05, P-06.

## Abstract parameters

The candidate can be specified without MUDAC-specific type ownership using abstract domains:

- `Evaluator`;
- `Subject`;
- `Scope`;
- `EvaluationBasis`;
- optional `OccurrenceContext`.

Whether these later synchronize to Participation, Team, Rubric and Encounter is not intrinsic to this candidate.

## Abstract state

For each logical obligation:

```text
obligation identity
scope
subject
evaluation basis
responsible evaluator
optional occurrence context
status
predecessor/successor relationship when reassigned
satisfying judgment reference, if satisfied
resolution reason/basis when excused/cancelled/reassigned
```

Working status vocabulary:

```text
Outstanding
Satisfied
Excused
Superseded by reassignment
Cancelled before required work
```

`Missing` is not a status invented to close an obligation; an unresolved required obligation remains Outstanding.

## Actions and queries

### `establish`
Creates an Outstanding obligation for one evaluator/subject/basis in a scope.

**Guard:** no conflicting current logical obligation may already represent the same required evaluation responsibility unless explicit policy permits multiple independent obligations.

**Effect:** obligation becomes current and Outstanding.

### `reassign`
Creates a successor obligation for a replacement evaluator and supersedes the predecessor as the current responsibility.

**Guard:** predecessor is still unresolved; reassignment is authorized for the relevant scope.

**Effect:** predecessor remains historical as Superseded; successor is Outstanding; no judgment authorship transfers.

### `excuse`
Resolves the obligation without evaluation evidence because the responsibility legitimately no longer applies.

**Guard:** obligation is Outstanding and the relevant semantic authority permits the excuse.

**Effect:** status becomes Excused with attributable basis. No zero or placeholder judgment is created.

### `cancel`
Ends a planned obligation before it becomes meaningful required evaluation work.

**Guard:** no authoritative judgment has satisfied it.

### `satisfy`
Associates one qualifying authoritative judgment with the obligation.

**Guard:** obligation is current/Outstanding and the supplied judgment matches the obligated evaluator, subject and basis semantics.

**Effect:** status becomes Satisfied; the same judgment does not create extra evaluation weight merely because assignment history exists.

### Queries

`status`, `outstandingFor(scope/subject/evaluator)`, `currentResponsibleEvaluator`, `obligationHistory`, `satisfyingJudgment`.

## Operational Principle

A live judging context establishes that Evaluator A is expected to judge Subject X. If A performs and finalizes the required independent judgment, the obligation becomes Satisfied. If A recuses before judging, the obligation is explicitly Excused or reassigned to B; it never becomes a zero. If reassigned, the historical expectation for A remains visible while B receives a new current obligation. At any moment the Organizer can distinguish work that is truly still outstanding from work legitimately resolved without a judgment.

## Invariants

1. Excused or cancelled work is not evaluation evidence.
2. Reassignment does not rewrite who was originally responsible.
3. Reassignment never transfers semantic authorship of an existing judgment.
4. A satisfied logical obligation references at most one qualifying independent judgment for that responsibility.
5. An outstanding obligation cannot silently disappear because an occurrence/group membership changed elsewhere.
6. Satisfaction and evaluation weight are distinct; history must not multiply a single judgment.

## Deliberate under-specification / 010-F questions

- whether obligations exist before an evaluation occurrence or are created only at occurrence start;
- whether one obligation is always individual or may express a group/capacity requirement;
- whether the candidate's purpose is already fully served by Judging Encounter participant/obligation state;
- whether assignment is user-facing enough to be a Concept rather than subordinate coordination state.

**010-E disposition:** behaviorally sufficient challenger for 010-F; not promoted.

# Challenger C2 — Evaluation Sufficiency

## Purpose

Determine whether a declared body of qualifying evaluation evidence is sufficient for a stated competition decision purpose, while allowing an explicitly governed exception to change eligibility **without falsifying the observed shortfall**.

Purpose pressure: P-02, P-04, P-06, P-07.

## Abstract parameters

- `Subject`;
- `DecisionPurpose`;
- `EvidenceFact`;
- `RequirementBasis`;
- `Authority` for exceptional acceptance.

## Abstract state

```text
assessment subject/scope
purpose
requirement basis identity
observed qualifying evidence facts
required conditions
current assessment status
exception decision, if any
assessment/exception history needed to explain current eligibility
```

Working status vocabulary:

```text
Satisfied
Incomplete
Exception Accepted
```

Observed facts remain distinct from the interpreted status.

## Actions and queries

### `assess`
Evaluates current evidence facts against the current requirement basis.

**Effect:** returns Satisfied or Incomplete unless an applicable current exception changes eligibility.

### `acceptException`
Records an authorized decision allowing the target decision purpose to proceed despite a known shortfall.

**Guard:** a real shortfall exists; policy permits an exception; authority/reason/scope are explicit.

**Effect:** status becomes Exception Accepted while observed evidence and expected requirement remain unchanged.

### `withdrawOrSupersedeException`
Ends the current exception decision when it was erroneous, no longer applicable, or replaced by another authorized decision.

### `reassess`
Re-evaluates after evidence or requirement basis changes.

**Effect:** prior assessments remain explainable; stale interpretation cannot masquerade as current.

### Queries

`status`, `observedFacts`, `shortfalls`, `requirementBasis`, `exceptionBasis`, `isEligibleFor(purpose)`.

## Operational Principle

The competition requires a declared amount/composition of qualifying evaluation before a Team may participate in an official ranking. The application measures the actual evidence. A Team meeting the declared conditions is Satisfied. Another Team is short because of a legitimate event disruption and remains Incomplete until an authorized Organizer accepts exactly that shortfall under policy. The Team then becomes eligible through `Exception Accepted`, while the system continues to show the real observed shortfall rather than pretending the missing evaluations existed.

## Invariants

1. Missing evidence is never converted into zero or fabricated evidence.
2. Exception acceptance changes permitted consequence/eligibility, not historical facts.
3. Sufficiency is independent from numerical Aggregate value.
4. A source-evidence or requirement-basis change invalidates any unsupported stale assessment.
5. An exception applies only to its declared subject, purpose and shortfall scope.
6. Satisfied and Exception Accepted remain semantically distinguishable.

## Deliberate under-specification / 010-F questions

- whether the concept owns enough state beyond the exception decision to justify Concept status;
- whether ordinary assessment is better understood as a derived mechanism over evidence + Evaluation Policy;
- whether the stateful exception should instead belong to a policy/exception concept while sufficiency stays derived;
- whether the candidate can be genericized beyond current Team-ranking Coverage without losing familiarity.

**010-E disposition:** behaviorally sufficient challenger for 010-F; current `Coverage` classification remains incumbent only.

# Challenger C3 — Reconciliation / Resolution

## Purpose

Represent the explicit resolution of a materially outcome-affecting discrepancy, shortfall or unresolved condition so consequential closeout can distinguish **truly resolved source truth** from a merely acknowledged checklist item.

Purpose pressure: P-04, P-06, P-07.

## Abstract parameters

- `Subject` / `Scope`;
- `SourceCondition`;
- `ConsequenceGate`;
- `ResolutionBasis`;
- `Authority` where an exception/disposition requires one.

## Abstract state

```text
resolution-item identity
scope/subject
source condition identity/class
current source-condition observation
consequence/blocking classification
status
resolution basis, if resolved
exception/not-applicable authority and reason, if relevant
opened/resolved/reopened/superseded history
```

Working states:

```text
Open
Resolved by source correction/change
Exception Accepted
Not Applicable
Superseded
```

A generic user-controlled `Done` state is intentionally excluded.

## Actions and queries

### `identify`
Creates/exposes an Open resolution item from a material current source condition.

### `refreshFromSource`
Re-evaluates whether the underlying condition still exists.

**Effect:** source correction may make the item Resolved; recurrence/material change may reopen or supersede it.

### `resolveBySourceChange`
Recognizes that the authoritative source condition has actually been corrected, invalidated, replaced or otherwise brought into an acceptable state.

**Guard:** the relevant source state now proves the blocking condition is resolved.

### `acceptException`
Records an explicit governed decision that the known condition may have a permitted consequence without changing the condition itself.

### `markNotApplicable`
Records that the item does not apply to the relevant decision scope, with inspectable basis.

### `reopen`
Restores Open status if new source information invalidates the prior resolution.

### Queries

`openItems`, `blockingItems`, `status`, `sourceCondition`, `resolutionBasis`, `history`.

## Operational Principle

After live judging, the system identifies that one outcome-affecting condition is unresolved—for example missing expected captured evidence, incompatible evaluation basis, an invalid occurrence without replacement, or a pending exception. An Organizer does not merely click a checkbox. The item becomes resolved only when the source is corrected/replaced or when an explicit governed exception changes what may proceed. Finalization can ask whether any blocking resolution items remain without treating the resolution item itself as the underlying evidence.

## Invariants

1. A resolution item never substitutes for or rewrites its source evidence.
2. Acknowledgement/hiding alone cannot make a blocking condition Resolved.
3. Exception acceptance preserves the source condition and its shortfall.
4. Reopening preserves the previous resolution history and basis.
5. Resolution status must be explainable from source truth or explicit governed disposition.
6. The candidate cannot become a generic project/task/ticket system detached from consequential competition semantics.

## Deliberate under-specification / 010-F questions

- whether durable resolution-item identity is truly user/domain value or only an experience projection over source conditions;
- whether each source Concept/policy plus readiness derivation already owns enough behavior to make Reconciliation a work mode only;
- whether `Not Applicable` and exception semantics belong elsewhere;
- whether this candidate is too generic unless restricted to outcome-authority closeout.

**010-E disposition:** behaviorally sufficient challenger for 010-F; not promoted.

# Challenger C4 — Official Outcome / Outcome Declaration

## Purpose

Establish and preserve an explicit authoritative declaration of competition outcomes, distinct from provisional calculations and distinct from external publication, so later correction can create a successor declaration without erasing what was previously official.

Purpose pressure: P-06, P-07, P-09.

## Abstract parameters

- `Scope`;
- `OutcomeBasis`;
- `DeclaringAuthority`;
- `OutcomeComponent`.

The candidate does not intrinsically require particular Rank/Award/Coverage types; those can be supplied later through composition.

## Abstract state

For each declaration lineage:

```text
declaration identity
scope
immutable declared outcome basis/components
declaring authority
declaration time
status/currentness
predecessor/successor relationship
materially affected marker/basis when current source truth has changed
```

Working currentness meanings:

```text
Current declared official
Affected but still latest declared official
Superseded official history
```

## Actions and queries

### `declare`
Creates the first immutable official declaration for a scope.

**Guard:** semantic authority is permitted to declare and all external finalization/readiness conditions have been satisfied through application composition.

**Effect:** the declaration becomes the current official declaration for the scope.

### `identifyAffected`
Marks that later verified source/policy change means the current official declaration's basis is no longer the current best-known basis.

**Effect:** declaration remains the latest declared official authority until explicitly superseded; it is not silently rewritten.

### `confirmSuccessor`
Creates an immutable successor declaration based on the corrected/reconciled outcome basis.

**Guard:** successor basis is explicitly confirmed by legitimate declaration authority.

**Effect:** successor becomes current; predecessor becomes Superseded official history.

### Queries

`currentDeclaration`, `declarationByIdentity`, `history`, `basis`, `isAffected`, `reconstructDeclaredOutcome`.

## Operational Principle

After live judging and reconciliation, an authorized Organizer explicitly confirms the competition outcome. The resulting declaration records the exact authoritative basis and becomes official even though it is not automatically public. Months later a verified source correction changes the calculated outcome. The previous declaration remains the latest declared official outcome but is visibly Affected while correction/reconciliation occurs. Only explicit successor confirmation establishes a corrected official declaration; the predecessor remains reconstructible as historical official truth.

## Invariants

1. A declaration is immutable once established.
2. Calculated/provisional values do not become official without explicit declaration authority.
3. A later source change does not silently mutate or revoke the historical declaration.
4. At most one declaration is the current declared official authority for the same scope/lineage.
5. Affected is not equivalent to Superseded; the prior declaration remains latest official until a successor is confirmed.
6. Publication/release is independent from official internal declaration.
7. A successor must retain an explicit relationship to the predecessor it replaces.

## Deliberate under-specification / 010-F questions

- whether explicit declaration/succession is independently valuable enough for Concept status or is fully a Competition Finalization effect plus Versioning/Provenance;
- whether `Official Outcome` risks becoming the rejected catch-all `Result` if its components are treated as owned state rather than identified declaration basis;
- whether the candidate should be genericized to `Declaration` or kept competition-specific;
- whether the current `Official Outcome Revision` mechanism already expresses exactly the right non-Concept role.

**010-E disposition:** behaviorally sufficient challenger for 010-F; current mechanism classification remains incumbent only.

# Merge/reframe comparison models for 010-F

These are not additional promoted candidates. They are behaviorally explicit countermodels required so 010-F can test real alternatives rather than assert that existing splits are self-evident.

## M1 — Actor Context

**Purpose hypothesis:** give a person one coherent current context answering who they are here, why they are participating and what they may currently do/see.

**State hypothesis:** stable person continuity + scoped capacity/role + lifecycle + current/exceptional capability/disclosure state.

**Actions:** establish/recognize person, enter scope/capacity, activate/complete/withdraw capacity, grant/revoke/expire capability, switch active context.

**OP:** a returning volunteer enters this Competition as a Judge; the system knows both the person's continuity and current capacity and derives/holds the capabilities appropriate to that context until event completion.

**Specification finding:** feasible to describe, but it combines three lifecycles that change for different reasons: cross-event human continuity, event-scoped participation, and resource/time-specific permission. This makes it a strong 010-F **over-combination countermodel**, not an obviously superior replacement.

## M2 — Evaluation Work Item

**Purpose hypothesis:** carry one unit of judging work from assignment through occurrence and final judgment.

**State hypothesis:** assigned evaluator(s), subject/basis, work status, occurrence context, individual judgment content/status.

**Actions:** assign, begin, adjust evaluator, record judgment, finalize, excuse/reassign, invalidate.

**OP:** an Organizer assigns judging work, the work begins when the subject is presented, and each evaluator completes the work item by finalizing judgment.

**Specification finding:** simple as a task mental model, but it combines shared occurrence truth with independently authored judgments and risks one work item having multiple semantic authors. This remains a strong negative/merge alternative for 010-F.

## M3 — Generic Evaluation Occurrence

**Purpose hypothesis:** preserve a bounded occurrence in which one or more evaluators assess a subject under a fixed presented context/basis, without intrinsically requiring `Panel` or `Team` types.

**State hypothesis:** occurrence identity; generic subject; generic evaluator participant snapshot/adjustments; presented context/basis; lifecycle; validity/invalidation/replacement; optional obligation relationships.

**Actions:** prepare, begin, recordParticipantAdjustment, complete, cancel, invalidate, linkReplacement.

**OP:** evaluators begin one shared occurrence, the occurrence snapshots what/who was being evaluated and who actually participated, later adjustments are explicit, and completion/invalidation preserves historical truth.

**Specification finding:** behavior maps cleanly onto current Judging Encounter while removing intrinsic `Panel + Team` naming. 010-F/010-G must decide whether this is merely generic parameterization of the same Concept or a meaningful reframe.

## M4 — Authority History

**Purpose hypothesis:** preserve both what authoritative states existed and how/why/through whose authority they arose.

**State hypothesis:** one lineage containing immutable state snapshots plus explanatory origin/authority events and correction relationships.

**Actions:** initialize, commit successor, invalidate, record origin/reason/authority, trace current/history/correction.

**OP:** an authoritative object is first established, later corrected through a successor, and a user can inspect both every authoritative state and the actor/source/reason lineage that produced each state.

**Specification finding:** behavior is coherent enough to compare, but it combines content-state history and explanatory event history with different minimal-state and query requirements. 010-F must test whether this is one coherent purpose or a convenience bundle.

## M5 — External Representation & Release

**Purpose hypothesis:** externalize identified source truth to a declared audience and govern whether that representation is currently released.

**State hypothesis:** source-bound representation identity/currency + disclosure profile + audience/channel + release/withdraw/supersession history.

**Actions:** generate, retrieve, regenerateFromCurrentSource, publish, withdraw, supersede release.

**OP:** an Organizer produces an audience-appropriate representation and deliberately releases it; if source truth later changes, the old representation/release remains historical while a corrected successor representation may be generated and explicitly released.

**Specification finding:** a coherent lifecycle can be written, but source-representation currency and distribution authority change independently. 010-F must decide whether the combined purpose remains singular or recreates the ambiguity that `Export`/`Publication` separation solved.

# Reassessment of derived/non-Concept subjects after behavioral specification

## Aggregate — remains derived for 010-F baseline

Its state is deterministically computed from eligible authoritative judgments and policy. There is no independent user-authored lifecycle/action beyond query/recomputation. No new specification evidence supports promotion.

## Rank — remains derived for 010-F baseline

Ordering is determined from rank-eligible subjects, Aggregate and declared comparison/tie policy. Direct editing would contradict its meaning. No independent Concept behavior emerged.

## Readiness — remains derived for 010-F baseline

Readiness answers whether a consequential next action may proceed from current authoritative state/policy. Acknowledgement does not change source truth. It remains a projection/gate rather than an independently operated subject.

## Recovery / Continuity — remains a cross-cutting completeness obligation

010-E confirms that current behavioral specifications expose the ingredients required to reason about P-05 without a standalone Recovery Concept:

- Scorecard Draft versus authoritative Finalization;
- obligation Outstanding versus Satisfied/Excused;
- Encounter participant/validity history;
- Provenance distinction between semantic author and capture actor/source;
- Versioning successor/current authority;
- Access expiry/reactivation boundaries;
- Export/Publication historical succession.

Unknown technical commit/result handling remains an implementation/concurrency concern constrained by the conceptual rule that uncertainty must not be mislabeled as semantic success.

**Decision:** do not promote Recovery in 010-E. Reopen only if 010-F/G reveal a missing coherent user-facing behavior that cannot be owned by the retained concepts.
