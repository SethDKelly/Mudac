# Purpose

Determine whether the behaviorally specified candidate boundaries entering 010-F each serve **one coherent valuable purpose**, and correct boundaries that are either overloaded or fragmentary before 010-G tests completeness, independence and boundary genericity.

010-F asks:

> If the implementation, current folder taxonomy and historical sixteen-Concept catalog disappeared, would each candidate still make sense as one user/domain functional unit whose behavior is wanted for one specific valuable purpose?

The governing rule comes from the adopted Base/Jackson modularity contract:

- **overloaded** candidates fail when separable behaviors serve different purposes merely because they concern the same domain noun, screen, workflow or historical implementation;
- **fragmentary** candidates fail when the proposed unit has no meaningful value until paired with another fragment that is really part of the same purpose;
- frequent interaction is not a reason to combine Concepts;
- shared implementation/storage/UI structure is not evidence of conceptual unity.

# Scope discipline

010-F evaluates **specificity and purpose singularity only**.

It does not yet decide whether a surviving candidate:

- contains every behavior needed to fulfill its purpose;
- can be specified independently of every peer Concept;
- should replace direct application-specific types with generic parameters;
- belongs in every coherent MUDAC product variant;
- has the best familiar/reusable name;
- composes correctly with every peer Concept.

Those questions belong to 010-G, Phase 012, Phase 014 and Phase 011 respectively.

A 010-F disposition is therefore a **provisional specificity decision**. It is binding input to 010-G but is not yet canonical promotion/demotion. 010-H owns canonical reconciliation after 010-G has tested the resulting boundaries.

# Decision vocabulary

- **RETAIN** — current purpose boundary is singular enough to continue.
- **RETAIN + REDUCE** — the Concept survives, but behavior serving a different purpose must leave the boundary.
- **SPLIT** — one current boundary contains separable purposes that should continue as different candidates.
- **REFRAME** — the behavior is coherent, but its current semantic label/boundary emphasizes the wrong unit.
- **REJECT AS CONCEPT** — the candidate does not survive specificity as an independently valuable Concept; its behavior may remain a mechanism, policy, process or subordinate state.
- **REJECT MERGE** — the proposed combined countermodel would overload one Concept with separable purposes.

# Headline result

010-F changes the candidate shape materially.

The sixteen incumbent Concepts do **not** survive unchanged as the only candidate set.

The principal decisions are:

1. current **Judging Encounter** is **split** into a bounded historical **Evaluation Occurrence** purpose and a separate **Evaluation Obligation** purpose;
2. **Evaluation Assignment / Obligation** survives, reframed to **Evaluation Obligation** because assignment/reassignment are actions within the responsibility lifecycle rather than a second purpose;
3. **Official Outcome / Outcome Declaration** survives, reframed to **Outcome Declaration**, and Competition is correspondingly reduced so it owns lifecycle Finalization but not the identity/history of declared outcome content;
4. **Evaluation Sufficiency** does **not** survive as a Concept: assessment is derived, while governed exception acceptance is a different authority decision;
5. **Reconciliation / Resolution** does **not** survive as a Concept: it remains an Organizer work mode/process over source conditions rather than an independently meaningful source of truth;
6. Actor Context, Evaluation Work Item, Authority History, and External Representation & Release are rejected as merges because they combine behavior with independently varying purposes/lifecycles;
7. the remaining incumbent boundaries survive specificity and proceed to 010-G.

The provisional post-010-F candidate set contains **eighteen** candidates for 010-G. This is not yet the canonical catalog.

# Detailed boundary decisions

## 1. Competition versus Outcome Declaration

### Current pressure

Competition currently owns the occurrence lifecycle:

`Draft → Ready → Active → Event Completed → Finalized`

and its current Operational Principle says explicit Finalization establishes the Competition as finalized with an identified official outcome basis.

The separate official-outcome behavior established in 010-E has a different lifecycle:

- declare an immutable official outcome basis;
- remain the latest declared official state even if later source truth makes it Affected;
- establish a successor declaration only through explicit authority;
- preserve superseded official history while Competition remains Finalized.

### Counterexample

A post-finalization source correction can alter the current best-known outcome basis while the Competition **does not leave Finalized**.

Therefore:

```text
Competition lifecycle state
        and
current declared outcome authority
```

can change independently.

That is strong specificity evidence that the content/identity/history of an official outcome declaration is not merely another field in Competition lifecycle state.

### Decision

**Competition RETAIN + REDUCE.**

Competition keeps the specific purpose:

> Establish the lifecycle and governing context of one competition occurrence.

`finalize` remains a Competition lifecycle action because Finalized is a meaningful occurrence-level authority boundary.

Competition does **not** own the identity, immutable content basis, Affected status, predecessor/successor lineage or reconstruction semantics of declared official outcomes.

**Outcome Declaration survives as a separate candidate** with the specific purpose:

> Establish and preserve an explicit authoritative declaration of supplied outcome meaning, including successor declaration after legitimate correction, without becoming the calculation or publication itself.

Whether Competition Finalization and Outcome Declaration must synchronize is deliberately deferred to Phase 011.

## 2. Panel, Evaluation Occurrence, Evaluation Obligation and Scorecard

This is the largest specificity correction in 010-F.

### Four different purposes are present

**Panel** answers:

> Which evaluators are intended to operate together as a reusable current group?

**Evaluation Occurrence** answers:

> What bounded judging occurrence actually happened, under what presented context, with which actual participants, and was that occurrence valid/cancelled/invalidated/replaced?

**Evaluation Obligation** answers:

> Which evaluator is currently responsible for producing one qualifying independent evaluation for a subject/basis, and is that responsibility Outstanding, Satisfied, Excused, Cancelled or superseded by reassignment?

**Scorecard** answers:

> What independent judgment did one evaluator author, and what Draft/Finalized/Amendment authority state does that judgment have?

These are not four names for one workflow. They answer different user/domain questions.

### Why current Judging Encounter is overloaded

The current Encounter records:

- the occurrence and presented context;
- actual participant history;
- **evaluation-obligation state**;
- completion when all required obligations are resolved.

But occurrence completion and evaluation responsibility can diverge.

Examples:

- a presentation ends while one Judge legitimately finishes a Scorecard afterward;
- an obligation can be reassigned without changing that the original occurrence happened;
- a Judge can be excused from an obligation without erasing that the Judge appeared in the occurrence's starting context;
- a replacement/rejudge occurrence can be created while prior obligation history remains meaningful;
- an ad hoc occurrence can be meaningful without requiring a reusable Panel as its intrinsic subject type.

The historical occurrence therefore should not remain open merely because individual evaluation work is unfinished, and an obligation should not disappear merely because occurrence membership changes elsewhere.

### Decision

**Panel RETAIN.** It owns reusable intended grouping only.

**Judging Encounter SPLIT + REFRAME.** The post-specificity occurrence candidate is provisionally named **Evaluation Occurrence**.

Its purpose is limited to preserving the bounded historical evaluation occurrence and its actual presented/participant/validity context. It should no longer own evaluator responsibility status merely to know when individual Scorecards are finished.

**Evaluation Assignment / Obligation is reframed to Evaluation Obligation and RETAINED as a candidate.**

`assign`/`reassign` are lifecycle actions. The Concept purpose is the responsibility/expectation itself, not the administrative act of assignment.

**Scorecard RETAIN.** A responsibility can exist before judgment; a judgment can remain historically authoritative after responsibility state changes; one Concept must not transfer evaluator authorship to satisfy coordination needs.

### Explicit rejected merge — Evaluation Work Item

The Evaluation Work Item countermodel combines shared occurrence truth, individual responsibility and independently authored judgment.

It fails specificity because:

- shared occurrence state has multiple participants;
- each obligation has one responsible evaluator;
- each Scorecard has one semantic author;
- occurrence invalidation, obligation reassignment and judgment amendment change for different reasons.

**Decision: REJECT MERGE.**

## 3. Identity, Participation and Access versus Actor Context

The Actor Context alternative asks whether MUDAC should model one object meaning "who I am here and what I may currently do."

That is convenient as an experience concept, but it combines three separable purposes:

- **Identity** — continuity of the human across participation episodes;
- **Participation** — scoped, time-bounded capacity in one competition;
- **Access** — current capability/disclosure permission under resource, relationship, state, purpose and time.

Counterexamples are straightforward:

- Identity can remain established while all Participation is complete;
- Participation can remain historically valid while ordinary Access expires;
- temporary Access can be revoked/expired without changing Identity or Participation;
- the same Identity can have multiple Participation capacities;
- switching Participation context changes Access without changing human continuity.

**Decision: RETAIN Identity, Participation and Access separately. REJECT Actor Context as a combined Concept.**

Actor Context may remain a later mapping/experience composition if useful; Phase 013 owns that question.

## 4. Versioning and Provenance versus Authority History

Authority History can be described coherently at a high level, but the combined purpose is plural:

- Versioning answers **what authoritative states existed and which state is current**;
- Provenance answers **how, why, from what source and through whose semantic authority state arose**.

Counterexamples:

- a subject can have multiple Versions with minimal explanatory provenance;
- meaningful provenance can exist for actions that do not create a Version;
- invalidation/replacement provenance may explain changes across distinct logical subjects rather than one Version lineage;
- snapshot comparison and origin/authority tracing are different user questions.

**Decision: RETAIN Versioning and Provenance. REJECT Authority History merge.**

This does not yet establish that either is sufficiently independent/generic as a peer Concept; 010-G owns that test.

## 5. Export and Publication versus External Representation & Release

A unified External Representation & Release lifecycle is possible to write, but it bundles two purposes that can vary independently:

- **Export** — create and preserve a representation tied to an identified source/purpose/audience disclosure basis;
- **Publication** — deliberately make an identified representation available to an audience/channel and later withdraw/supersede that release.

Counterexamples:

- an Export may be generated for preview, print, audit, contingency or internal use and never Published;
- a source correction can make an Export stale while its historical Publication remains a fact;
- withdrawing a Publication does not alter the bytes/source basis of the Export;
- generating a replacement Export does not automatically publish it.

**Decision: RETAIN Export and Publication separately. REJECT External Representation & Release merge.**

## 6. Division

Division is not rejected merely because some future product variant could omit competitive cohorts.

Its specific purpose is:

> Define a comparison cohort and maintain the current competitor assignment needed to know which subjects belong to that cohort.

Definition and assignment are not two unrelated purposes; assignment is how the cohort's membership becomes meaningful.

Whether Division is optional in some MUDAC application family belongs to Phase 012.

**Decision: RETAIN.**

## 7. Alias

Alias is more than a Team display field because it has independent replacement, uniqueness, non-reuse, historical resolution and disclosure-sensitive use semantics.

The purpose remains singular:

> Maintain a context-specific alternate identity that can be used without exposing the underlying identity.

Whether the Concept should later be parameterized over arbitrary subjects/scopes belongs to 010-G.

**Decision: RETAIN.**

## 8. Access

Access combines ordinary contextual decision and explicit exceptional grant/revoke/expiry behavior, but both serve the same purpose:

> Control whether a principal/context may perform or receive a protected capability/disclosure now.

This differs from Evaluation Sufficiency below: an Access grant changes Access under the same purpose; a sufficiency exception does **not** make missing evidence sufficient—it changes whether a later decision may proceed despite insufficiency.

**Decision: RETAIN Access for 010-G.**

## 9. Award

Award definition, conferral, revocation and correction all serve one recognition purpose.

A definition is preparation for meaningful recognition; conferral applies that same recognition semantics. Rank-derived and discretionary selection are different selection methods, not different Concept purposes.

**Decision: RETAIN.**

# Challenger decisions

## Evaluation Obligation — RETAIN

010-E demonstrated a singular valuable purpose:

> Maintain one evaluator's current responsibility to produce a qualifying independent evaluation, distinguishing Outstanding, Satisfied, Excused, Cancelled and Reassigned responsibility without fabricating judgment evidence.

This purpose is separable from occurrence history and from the judgment itself.

The working name is reduced from **Evaluation Assignment / Obligation** to **Evaluation Obligation** because assignment/reassignment describe actions that establish/change the obligation rather than a second semantic object.

**010-F disposition: RETAIN as a provisional candidate for 010-G.**

## Evaluation Sufficiency — REJECT AS CONCEPT

The 010-E challenger combined:

1. derived assessment of observed qualifying evidence against requirements; and
2. authority to accept an exception that permits a downstream purpose to proceed despite a known shortfall.

Those are not one purpose.

The first is a calculation/projection:

> Are the current qualifying facts sufficient under the declared requirement basis?

The second is a governance decision:

> May this consequence proceed despite known insufficiency?

An exception must preserve that evidence is still insufficient; therefore it cannot semantically be the same state transition as making sufficiency `Satisfied`.

Splitting the candidate does **not** reveal two Concepts:

- Evaluation Sufficiency remains appropriately derived from evidence + requirement basis;
- governed exception authority remains policy/decision/provenance behavior unless later phases expose an independently valuable reusable exception Concept.

The current `Coverage` mechanism therefore remains the incumbent home for evaluation-sufficiency semantics, but 010-H should correct any presentation that treats `Exception Accepted` as if it were the same factual dimension as raw `Satisfied`/`Incomplete` sufficiency.

**010-F disposition: REJECT AS CONCEPT; retain as derived mechanism pressure.**

## Reconciliation / Resolution — REJECT AS CONCEPT

The proposed durable resolution item becomes valuable only because some underlying source condition is unresolved.

When the source is corrected, invalidated, replaced or governed by an explicit exception, the meaningful change occurs in the source Concept/policy/authority decision—not in a separate reconciliation object.

If Reconciliation owns independent open/resolve/reopen state unrelated to source truth, it becomes a generic task/ticket purpose. If it does not, it remains a process/projection over source state.

That is exactly the current canonical interpretation: Organizer work mode, not independent source state.

**010-F disposition: REJECT AS CONCEPT; retain Reconciliation as process/mechanism/experience.**

## Official Outcome / Outcome Declaration — RETAIN + REFRAME

The candidate is too broad if named simply `Official Outcome`, because that name invites Aggregate, Coverage, Rank, Awards and other result semantics back into one catch-all.

The behavior that survives specificity is narrower and singular:

> Establish and preserve an explicit authoritative declaration over an identified outcome basis, including Affected and successor-declaration history after correction.

The candidate therefore proceeds under the working name **Outcome Declaration**.

It does not own how scores are aggregated, how Teams rank, which Awards exist, or how information is published. It owns the authority-bearing act/state that makes a supplied outcome basis officially declared and preserves successor history.

**010-F disposition: RETAIN + REFRAME as Outcome Declaration for 010-G.**

# Historical 007-B comparison

007-B previously retained all fifteen then-current Concepts and promoted Publication as the sixteenth. That work remains valuable behavioral evidence, especially its Export/Publication split.

010-F reaches a different conclusion at the judging/outcome seams because the reopened methodology corrected the order of operations:

1. project/purpose truth was re-established independently of the catalog;
2. candidates were rediscovered divergently;
3. challenger/countermodel behavior was specified before modularity;
4. specificity is now evaluated explicitly before completeness/independence.

The new Judging Encounter split and Outcome Declaration candidate are therefore not changes made for novelty. They follow from counterexamples that were not modeled as first-class candidate alternatives in 007-B.

# Re-specification debt created by 010-F

If 010-G does not overturn these specificity decisions, 010-H must re-specify and canonically reconcile at least the following:

## Competition

Reduce official-outcome ownership language while preserving Finalized as Competition lifecycle state. Identify later synchronization to Outcome Declaration without embedding declaration state.

## Judging Encounter → Evaluation Occurrence

Re-specify purpose, state, lifecycle and actions around the occurrence itself. Remove evaluator-obligation status and the rule that occurrence completion waits for all Scorecard obligations.

Participant snapshots/adjustments remain only to preserve what actually happened in the occurrence.

## Evaluation Obligation

Create a canonical specification only if 010-G confirms completeness/independence. Preserve Outstanding/Satisfied/Excused/Cancelled/Reassigned history without creating placeholder judgment or transferring authorship.

## Outcome Declaration

Create a canonical specification only if 010-G confirms completeness/independence. It must own declaration identity/currentness/Affected/successor history without absorbing Aggregate, Rank, Award, Competition lifecycle or Publication.

## Coverage / Evaluation Sufficiency

Preserve derived factual sufficiency separately from governed exception disposition so an accepted exception never reads as fabricated evidence satisfaction.

## Reconciliation

Retain as work mode/process over source conditions; do not introduce generic ticket-state authority merely for workflow convenience.

# 010-F exit test

010-F may pass only if:

- every incumbent and 010-E challenger receives an explicit specificity disposition;
- all five principal merge/reframe countermodels are decided behaviorally;
- overloaded Concepts are split/reduced rather than protected by chronology;
- fragmentary/derived/process candidates are not promoted merely because users see their status;
- decisions explain the protected purpose and counterexample, not an arbitrary score;
- optional product-scope questions are deferred to Phase 012 rather than used to reject otherwise specific Concepts;
- independence/genericity questions remain visible for 010-G rather than being falsely closed here;
- canonical promotion/demotion is deferred until 010-H convergence;
- no architecture, implementation, schema, UI route, API, persistence or AWS choice determines the boundary;
- 010-G has one explicit post-specificity candidate set to test.

All conditions are satisfied.
